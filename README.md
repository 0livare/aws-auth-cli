# AWS Auth Helper CLI

`aws-auth` makes authenticating with AWS in the command line easier. It reads the role profiles in `~/.aws/credentials`, lets you pick one from an interactive list, assumes the role with MFA (fetching the TOTP code from 1Password), and points `AWS_PROFILE` at the resulting session.

## Profiles

`aws-auth` works with standard AWS role profiles. Use them exactly as they are:

```ini
# ~/.aws/credentials
[iam-user]
aws_access_key_id = AKIA...
aws_secret_access_key = ...

[staging]
role_arn = arn:aws:iam::123456789012:role/DevRole
source_profile = iam-user
mfa_serial = arn:aws:iam::210987654321:mfa/username
# optional, defaults to 3600
duration_seconds = 14400
region = us-east-1
```

Keep comments on their own lines. The AWS CLI doesn't strip comments after a
value, so `duration_seconds = 14400  # optional` would be read as
`14400  # optional`, and the sign-in would fail.

Every section in `~/.aws/credentials` with a `role_arn` shows up in the picker.
Each role profile needs:

| Key                 | Purpose                                                                                                   |
| ------------------- | --------------------------------------------------------------------------------------------------------- |
| `role_arn`          | Role to assume                                                                                            |
| `source_profile`    | Profile with the long-term keys used to call `assume-role`                                                |
| `mfa_serial`        | Your MFA device                                                                                           |
| `duration_seconds`  | Session length (optional, default `3600`)                                                                 |
| `one_password_item` | 1Password item holding the MFA code (optional, inherited from `source_profile` or `[default]`, see below) |

### Session profiles

When you sign in to `staging`, `aws-auth` writes the
temporary credentials to a generated `[staging-session]`
profile and sets `AWS_PROFILE` to it. The session can't live in the role profile
itself: the AWS CLI would see `role_arn`, try to assume the role on its own, and
prompt for MFA instead of using the session.

The generated profile is a copy of the role profile (`region`, `output` and any
other settings) plus the session credentials. Settings that would make the AWS
CLI fetch credentials itself (`role_arn`, `source_profile`, `mfa_serial`,
`duration_seconds`, `credential_process`, SSO settings and existing keys) are
left out. It is rewritten in full on every sign-in, so change settings on the
role profile, not the `-session` one.

All `-session` profiles are kept together at the bottom of `~/.aws/credentials`,
below a few empty lines and a "Generated by aws-auth" comment. Nothing above
them is changed.

```ini
[staging]
role_arn = ...



# Generated by aws-auth (https://github.com/0livare/aws-auth-cli)
# The -session profiles below are rewritten on every sign-in; edit the
# original profiles above instead.
[staging-session]
aws_access_key_id = ASIA...
aws_secret_access_key = ...
aws_session_token = ...
region = us-east-1
```

You can refer to a profile by either name: `aws-auth -p staging` and
`aws-auth -p staging-session` do the same thing.

## 1Password setup

`aws-auth` can automatically fetch your MFA TOTP code from 1Password so you never have to type it manually. This integration is optional but highly recommended!

**Requirements:**

1. [1Password CLI](https://developer.1password.com/docs/cli) installed
2. Signed in to the 1Password CLI: `op signin` (required — `op item get` won't work without it)

Set `one_password_item` to the name of the 1Password item that holds your AWS
MFA code. It's looked up on the role profile first, then on its
`source_profile` (the IAM user that owns the MFA device), then under
`[default]`. Set it under `[default]` in `~/.aws/config` to apply it to every
profile, on a source profile to cover every role that uses it, or on a role
profile to override both for that profile:

```ini
# ~/.aws/config
[default]
one_password_item = AWS MFA
```

```ini
# ~/.aws/credentials — per-profile override (optional)
[prod-admin]
role_arn = ...
one_password_item = AWS Prod MFA
```

With this configured, `aws-auth -p <profile>` assumes the role with no token
argument. If 1Password can't provide the code, you're prompted to type the
six-digit code. If no `one_password_item` is set anywhere, `aws-auth` warns you,
and if the profile has no session yet it points `AWS_PROFILE` at the role
profile itself so the AWS CLI asks for the code when you run a command.

(`op_item` is accepted as an older spelling of `one_password_item`.)

## Usage

```sh
# Interactive profile selector (reads ~/.aws/credentials)
aws-auth

# Select a profile interactively and use a manual MFA token
aws-auth <token>

# Sign in to a profile, fetching the MFA code from 1Password
aws-auth -p <profile>

# Select a profile by its 12-digit AWS account ID
aws-auth -p 342327770208

# Sign in with a manual MFA token (bypasses 1Password)
aws-auth <token> -p <profile>

# Re-authenticate even if the profile still has a valid session
aws-auth -p <profile> --force

# Show every profile and its session status
aws-auth --list

# Unset the current profile (and forget it for --restore)
aws-auth --clear

# Set the last used profile, if its session is still valid
aws-auth --restore
```

### Multiple signed-in profiles

Each profile's session lives in its own `-session` profile, so any number of
profiles can be signed in at once. Switching to a profile whose session has more
than 5 minutes left just sets `AWS_PROFILE` — no MFA, no `assume-role`. Expired
(or nearly expired) sessions are re-authenticated automatically. Passing a manual
MFA token or `aws-auth -p <profile> --force` always re-authenticates.

The interactive picker and `aws-auth --list` show each profile's session status
(`● 42m left`, `○ expired`, `○ signed out`).

### Starting new shells in your last profile

`AWS_PROFILE` only exists in the shell that ran `aws-auth`, so a new terminal tab
starts with no profile. To have new shells pick up the profile you last used,
add `aws-auth --restore` to `~/.zshrc` after the wrapper:

```zsh
aws-auth() { eval "$(command aws-auth "$@")"; }
aws-auth --restore
```

Every time `aws-auth` sets a profile, it remembers it in `~/.aws/expiry/.last`;
whichever shell set one most recently wins. `--restore` sets that profile only
while its session has more than 5 minutes left, and otherwise does nothing, so a
new shell never starts with dead credentials. It reads two small files and
nothing else (no `aws` calls, no MFA, no output), so it doesn't slow down shell
startup. `aws-auth --clear` forgets the remembered profile.

### Selecting by account ID

`aws-auth -p` (or `--profile`) accepts either a profile name or the 12-digit AWS account ID
shown in parentheses in the picker. A unique account match selects that profile
directly. If multiple profiles share the account, an interactive picker shows only
those profiles. Without a terminal, ambiguous account IDs produce an error listing
the matching profile names; pass a profile name instead. An account ID with no
matches also produces an error. An exact profile name takes precedence over an
account ID match. Account ID selection supports manual MFA tokens and 1Password
in the same way as profile name selection.

## Troubleshooting

Before doing anything else, `aws-auth` checks `~/.aws/credentials` and
`~/.aws/config` for mistakes that stop the AWS CLI from reading them, and lists
each one with its line number:

- the same `[section]` twice in one file
- the same key twice in one section
- a `key = value` line before any `[section]`
- a line that isn't a section, a `key = value` pair or a comment

```
  ✖  ~/.aws/credentials is invalid, so the AWS CLI can't read it:
       line 8: [staging] appears more than once (first on line 5)
     Fix the file, then run aws-auth again.
```

It also warns about a comment after a value (`duration_seconds = 14400  # 4h`),
which the AWS CLI reads as part of the value. If the AWS CLI still reports a
problem `aws-auth` didn't catch, `aws-auth` shows the AWS CLI's own error.
