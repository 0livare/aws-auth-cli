The problem

Signing in to MFA-protected roles gets in the way.

Raw aws commands● interrupts you
1Asks for a code in the middle of your work$ export AWS_PROFILE=staging$ aws s3 lsEnter MFA code for arn:aws:iam::…:mfa/me: ▌…and again whenever the cached session expires2Tools that can't ask for a code just fail$ terraform planError: no valid credential sources foundTerraform, Docker and most SDKs can't show an MFA prompt
Old shell helper● manual & fragile
3A failed sign-in still switches your profile$ aws-profile staging -t 482913  # code copied by handERROR: assume-role returned empty credentials$ echo $AWS_PROFILEstagingYou're now pointed at a profile with no working session4Settings like region are dropped$ aws-profile sandbox -t 771204✓ [sandbox] authenticated$ aws s3 lsYou must specify a region.Only the three keys are written; the role's region is left behind
Speaker notes
  • ① ② Raw aws points AWS_PROFILE at the role profile, which has no credentials. Every tool must assume the role and ask for a code itself.
  • The AWS CLI and boto3 can ask; Terraform, Docker and the Node SDK usually can’t. The error text is illustrative.
  • ③ The helper exports AWS_PROFILE before signing in, so a failed sign-in still switches you.
  • ④ The helper writes only the three keys, so the role’s region is lost.

  • Plain aws-auth opens the picker; the MFA code comes from one_password_item.

  • If 1Password can’t supply a code it prompts you, or pass one directly: aws-auth 123456 -p staging.
What you get

Six small things that add up to never thinking about it.

01

No codes to type

The MFA code is read from 1Password with one_password_item. Set it once under [default] and it covers every role.

02

Every tool works

Sessions are ordinary credentials, so Terraform, Docker, SDKs and scripts work without MFA support of their own.

03

Profiles as written

Standard role profiles work unchanged. No -mfa copies, no renaming, no extra sections to maintain.

04

Many roles at once

Each role keeps its own session. Switching to one that's still valid is instant: no MFA, no network call.

05

Settings carried over

region, output and your other settings are copied into the session profile, so nothing goes missing.

06

Clear errors

Broken ~/.aws files are caught before anything runs, with the exact line and what's wrong with it.

Speaker notes
  • “Every tool works” is versus raw aws; the old helper also gives tools plain credentials.
  • Only aws-auth: 1Password codes, profiles used as written, settings copied, clear errors, and a failed sign-in never switches you.

Every role and how long its session has left, before you choose. Pick with the arrow keys, or skip the picker with aws-auth -p staging or the account ID, aws-auth -p 123456789012.

Speaker notes
  • ● time left, ○ expired, ○ signed out. Under 5 minutes left counts as expired and signs in again.
  • Switching to a role with a valid session is instant: no MFA, no network call.
  • -p takes a name or a 12-digit account ID; an ID shared by several roles shows just those.
Your credentials file

Your profiles stay yours. Ours stay at the bottom.

[iam-user] aws_access_key_id = AKIA… [staging] role_arn = arn:aws:iam::123456789012:role/DevRole source_profile = iam-user mfa_serial = arn:aws:iam::210987654321:mfa/me region = us-east-1
· · ·
# Generated by aws-auth # The -session profiles below are rewritten on every sign-in [staging-session] aws_access_key_id = ASIA… aws_session_token = … region = us-east-1

Above the line

Exactly what you wrote. aws-auth reads your role profiles and never edits them.

Below the line

One generated -session profile per role, grouped under a banner. It's a copy of the role's settings plus fresh credentials, rewritten on every sign-in.

Why two sections?

If session keys sat next to role_arn, the AWS CLI would ignore them and ask for MFA again.

Speaker notes
  • Your sections are only read, never edited.
  • Each -session profile is rewritten in full on sign-in, grouped at the bottom under the banner.
  • Everything is copied except keys that make the CLI fetch credentials itself (role_arn, mfa_serial, source_profile, SSO…).

Get started

Three steps. Then forget about it.

1

Install

$ bun install
$ bun link
2

Add the wrapper

# ~/.zshrc
aws-auth() {
  eval "$(command aws-auth "$@")"
}
3

Point at 1Password

# ~/.aws/config
[default]
one_password_item = AWS MFA

Then run aws-auth and pick a role.

Speaker notes
  • Needs Bun and the AWS CLI; the 1Password CLI is optional (run op signin once).
  • The wrapper exists because a program can’t change its parent shell’s environment.
  • one_password_item under [default] covers every role. Keep comments on their own lines in ~/.aws files.
